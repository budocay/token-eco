token-eco fournit à Claude Code des outils de lecture, recherche et édition de fichiers conçus pour renvoyer moins de tokens, un agent principal qui les impose, une consigne injectée aux sous-agents et un hook qui compacte les sorties Bash et redirige les lectures de gros fichiers. (1) Hors ligne, les outils renvoient 4 à 24 % de la taille d'une lecture complète avec une fidélité structurelle de 92 à 100 % (TS, JS, Python) ; la recherche compacte donne les mêmes résultats que grep pour 47 % de ses tokens. (2) En A/B mono-agent sur des tâches courtes (Sonnet), le coût baisse de 8 à 10 % sans perte de réussite (56/56). (3) Sur des sessions réelles scénarisées, aucune économie en dollars n'est démontrée avec Sonnet (−7 % à +22 % selon les runs) ; un run Opus donne −13 %. (4) En usage réel (30 jours), les outils n'étaient presque pas utilisés (4,7 % du fil principal, 1,2 % des sous-agents) : un autre plugin imposait son agent et des agents de projet n'y avaient pas accès. (5) Dans un banc multi-agents reproduisant cette situation (63 exécutions, toutes réussies), équiper le relecteur fait passer sa couverture de 0 % à 39–93 % ; sur des tâches courtes le coût ne change pas de façon mesurable, tandis que sur une tâche longue les variantes token-eco coûtent 19 à 48 % de moins, avec séparation complète des valeurs dans deux cas sur quatre (p = 0,10, minimum atteignable avec 3 essais). Une partie de ce gain vient de l'agent principal (moins de tours d'orchestration). Aucun résultat n'atteint le seuil de 5 % : ce sont des tendances cohérentes, pas des preuves.

01Contexte et questions

Dans Claude Code, chaque appel d'outil est un tour complet : le modèle relit tout le contexte (depuis le cache de prompt), puis le résultat de l'outil est ajouté au contexte et relu à chaque tour suivant. Le coût d'une session dépend donc de la taille des résultats, du nombre de tours et de la taille du contexte accumulé. token-eco cherche à réduire les deux premiers. Les mesures visent à répondre aux questions suivantes :

  • Q1 — Fidélité et taille : les outils renvoient-ils la bonne information, et combien de tokens économisent-ils par appel ?
  • Q2 — Coût en conditions contrôlées : à tâche égale, une session avec token-eco coûte-t-elle moins cher, sans perte de réussite ?
  • Q3 — Adoption réelle : dans l'usage quotidien, les agents appellent-ils vraiment ces outils ?
  • Q4 — Multi-agents : dans un projet où un orchestrateur délègue à des agents spécialisés, qu'apportent les outils, et selon la longueur de la tâche ?

03Méthode commune et définitions

  • Coût : total_cost_usd renvoyé par Claude Code en fin de session (sous-agents compris), c'est-à-dire le prix équivalent API. Les exécutions passent par un abonnement : ce montant mesure la consommation, il n'est pas facturé tel quel.
  • Tours : nombre de réponses du modèle (fil principal / sous-agents), lu dans les journaux de session (~/.claude/projects/), avec dédoublonnage des messages répartis sur plusieurs lignes.
  • Couverture : appels token-eco read/search/edit ÷ (ces appels + Read/Grep/Glob/Edit/MultiEdit natifs).
  • Lectures via Bash : appels Bash commençant par cat, head, tail, sed -n, grep, rg, find, awk ; taille = taille du résultat.
  • Réussite : vérification automatique propre à chaque tâche (réponse attendue, fichiers modifiés, suite de tests, test caché).
  • Référence étanche (« native ») : outils token-eco interdits, hook désactivé, et depuis le banc 6 la copie du plugin installée sur le compte désactivée (sans quoi son agent s'appliquait aussi à la référence — défaut détecté et corrigé le 27/10).
  • Statistiques : moyenne ± écart-type, minimum–maximum ; comparaison à la référence par un test de permutation exact bilatéral sur le coût. Avec 3 essais contre 3, il n'existe que 20 partitions : la plus petite valeur de p possible est 0,10, obtenue quand les 3 valeurs d'un groupe sont toutes inférieures aux 3 de l'autre (séparation complète). Aucune correction pour comparaisons multiples n'est appliquée ; aucun résultat ne serait significatif après correction.

Niveaux de preuve utilisés dans la synthèse : Établi mesure directe, reproductible, sans ambiguïté · Fort effet net et cohérent, petit échantillon · Indicatif tendance, variance élevée ou un seul run · Non démontré.

04Banc 1 — Qualité hors ligne (TS, JS, Python)

Objectif : Q1. Vérifier que le plan d'un fichier et la lecture d'un symbole sont fidèles, et mesurer leur taille par rapport à la lecture complète. Périmètre : 263 fichiers (zod et ajv en TypeScript, SDK MCP compilé en JavaScript, bibliothèque standard Python 3.15), 2 666 symboles. Méthode : comparaison à une vérité terrain issue de l'arbre syntaxique réel (compilateur TypeScript, module ast de Python) ; tokens estimés à 4 caractères par token ; référence = Read natif (2 000 lignes au plus). Gratuit, déterministe (npm run bench, 6,7 s).

Recherche compacte vs grep -rn (10 motifs sur zod) : décompte identique pour 10 motifs sur 10 ; 47,3 % des tokens de grep -rn au total, mais plus que grep -rn sur les motifs à 0–2 résultats (en-tête fixe), et plus que le Grep natif par défaut, qui ne renvoie que la liste des fichiers (104 tokens au total).

Conclusion : Établi les outils sont fidèles et renvoient 4 à 22 % de la taille d'une lecture complète. Limites : mesure de taille par appel, pas d'une session ; l'économie réelle dépend de ce que l'agent aurait lu à la place.

05Banc 2 — Qualité multi-langages

Objectif : Q1 hors des trois langages principaux. Périmètre : 15 langages, jusqu'à 50 fichiers chacun, dépôts open source. Méthode : vérité terrain universal-ctags (node bench/languages.ts).

Résultats globaux : rappel du plan 96,9 %, lecture de symbole exacte 92,8 %. Taille du plan : 4,6 % (shell) à 23,5 % (PHP) de la lecture complète. Points faibles mesurés : précision du plan en C (26,6 %, minorant car ctags ignore certaines déclarations), Java et C# (≈ 68 %), lecture de symbole en Elixir (40,3 % exacte). Swift, Scala et Dart : pas de vérité terrain disponible.

Conclusion : Établi fidélité élevée pour la plupart des langages, avec des faiblesses identifiées (C, Java, C#, Elixir).

08Observation 5 — Usage réel sur 30 jours

Nature : étude observationnelle, pas une expérience. Objectif : Q3. Périmètre : journaux Claude Code de l'auteur sur 30 jours, plusieurs projets, hors dossiers de benchmark et temporaires. Méthode : lecture des journaux par le tableau de bord du plugin.

Appels token-ecoAppels natifsCouverture
Fil principal214454,7 %
Sous-agents1129 6851,2 %

Économie estimée : environ 3,41 $ sur 4 283 $ (< 0,1 %) ; les sous-agents pesaient 44 % du coût. Causes identifiées dans les journaux : (a) un autre plugin imposait son propre agent principal, qui l'emportait sur token-eco:eco ; (b) les agents en lecture seule du projet (relecteurs, sécurité, architecture) n'avaient que Read, Grep, Glob, liste produite par un générateur du projet ; (c) les sous-agents lisaient via Bash : sur 9 680 appels, cat a renvoyé 8 Mo, sed -n 7 Mo, grep 4,8 Mo.

Après correction (même jour, autre plugin retiré, relecteurs équipés de read/search) : sur quelques heures d'un projet, un relecteur a utilisé token-eco pour 55 % de ses appels de fichiers (62 contre 50, 0 % avant) ; un agent producteur 21 % (50 contre 191).

Conclusion : Établi avant correction, les outils n'étaient presque pas utilisés : aucune économie ne pouvait en résulter, quelle que soit leur qualité. Indicatif l'adoption remonte une fois les causes levées (un projet, quelques heures).

09Banc 6 — Adoption multi-agents

Objectif : Q3 et Q4 en conditions contrôlées : reproduire la situation observée en usage réel, mesurer l'adoption des outils par des sous-agents et son effet sur le coût, selon la longueur de la tâche. Outil : server/bench/adoption.ts, statistiques server/bench/adoption-stats.ts.

9.1 Protocole

  • Projet de test (copie neuve dans /tmp à chaque exécution) : le serveur du plugin et ses 35 tests ; deux spécifications Markdown de 454 lignes (~3 600 tokens chacune) dont les exigences utiles sont enfouies au milieu ; un CLAUDE.md « tu es l'orchestrateur, tu délègues » ; un agent reviewer en lecture seule avec une liste tools: ; un agent producer sans liste.
  • Variantes : native (plugin désactivé, référence) ; eco-before (plugin, agent eco, hook ; relecteur limité à Read, Grep, Glob, situation avant correction) ; eco-after (idem, relecteur doté en plus de token-eco read/search).
  • Tâches : t6 faire relire le code au regard d'une spécification et lister 3 écarts cachés (vérifié : les 3 constantes et valeurs citées) ; t7 faire implémenter une exigence (vérifié : suite de tests + test caché) ; t8, tâche longue enchaîner 5 délégations (relecture, correction des 3 écarts, nouvelle relecture, implémentation, relecture finale ; vérifié : 3 constantes corrigées, suite complète et test caché).
  • Modèles : orchestrateur Sonnet 5.5 ou Opus 5.5 ; les sous-agents ont tourné sur Sonnet 5.5 dans tous les cas, via le réglage CLAUDE_CODE_SUBAGENT_MODEL du compte, comme en usage réel.
  • Contrôles : exécution écartée si l'agent principal n'est pas celui attendu, si la référence utilise token-eco, ou en cas d'erreur d'infrastructure (réseau, abonnement). Ordre fixe à chaque essai : native, eco-before, eco-after.
  • Exécutions : 63 valides, 63 réussies ; 5 écartées (perte de réseau, abonnement suspendu), relancées.

9.3 Diagnostic du surcoût de t6 avec Sonnet (+22 %)

Le surcoût est identique avec et sans relecteur équipé : il ne vient donc pas de l'accès aux outils. Analyse des journaux des 36 exécutions :

  • Pas un coût fixe de contexte : contexte du premier tour (médiane) — fil principal 27,5 K tokens en eco contre 33,0 K en native (l'agent eco retire des outils) ; sous-agent 23,2 K contre 21,1 K.
  • Pas un défaut de cache propre au plugin : sondes « Reply OK » (5 exécutions, ~0,50 $) — en changeant de dossier, environ 20 K tokens sont réécrits en cache dans les deux variantes ; dans le même dossier, tout est relu.
  • Cause : le hook. Décomposition (Sonnet, t6) : coût des sous-agents 0,05 $ en native contre 0,12–0,13 $ en eco. Le relecteur eco lisait la spécification ; le hook refusait (454 lignes > 300) en renvoyant le plan et en conseillant l'outil read que ce relecteur n'avait pas ; il relançait la lecture complète (autorisée à la seconde tentative), puis lisait 6 fichiers source en entier. Le relecteur natif lisait la spécification puis faisait une seule recherche ciblée (311 tokens).
  • Correctif v0.7.4 : la lecture complète n'est redirigée que si le fichier dépasse aussi 6 000 tokens. Une spécification Markdown de 454 lignes courtes (~3 600 tokens) n'est plus redirigée.

En une phrase : les outils sont bons et, quand ils sont réellement utilisés dans une session longue, la session coûte moins cher ; sur des tâches courtes l'effet est nul ou de l'ordre de 10 %, et en usage réel il reste à démontrer — la condition première est l'adoption.

11Menaces à la validité

  • Statistique : 3 essais par case (4 au banc 3) ; p minimal de 0,10 ; 14 comparaisons sans correction ; coefficients de variation de la référence de 14 à 21 % sur la tâche longue. Les ampleurs sont incertaines, seul le sens est cohérent.
  • Validité interne : ordre des variantes fixe (native, eco-before, eco-after) et non aléatoire : un effet d'ordre ou d'heure (charge de l'API, cache) n'est pas exclu ; variantes eco = plusieurs facteurs à la fois (agent, consigne, outils, hook) ; jusqu'au 27/10, la référence pouvait hériter de l'agent du plugin installé (bancs 3 et 4 potentiellement concernés, non vérifiable a posteriori) ; une exécution écartée à la main (coupure réseau en cours d'exécution).
  • Validité de construit : coût = prix équivalent API calculé par Claude Code ; couverture = nombre d'appels, pas tokens ; détection des lectures via Bash par motif de commande (heuristique) ; tokens estimés à 4 caractères (bancs 1–2).
  • Validité externe : projets de test petits (≈ 35 tests, 2 spécifications) et tâches conçues par l'auteur du plugin ; un seul utilisateur ; sous-agents toujours sur Sonnet ; versions de Claude Code 2.1.29x–2.1.31x, dont le comportement évolue ; une session réelle compte des centaines à des milliers de tours, contre 37 à 95 pour la tâche longue.

12Recommandations

  • Puissance : pour confirmer un effet de −30 % avec la variance observée, viser au moins 8 essais par variante sur la tâche longue.
  • Ordre aléatoire des variantes à chaque essai, et variante « agent eco seul, sans outils ni hook » pour séparer l'effet de l'agent principal de celui des outils.
  • Suivi réel sur deux semaines avec le tableau de bord (colonne Agent, couverture, coût par tour) après les corrections.
  • Déploiement : vérifier l'agent principal actif et donner read/search aux agents à liste tools: avant d'attendre une économie.

Glossaire

Couverture : part des appels de fichiers passant par token-eco. Orchestrateur : fil principal qui délègue. Sous-agent : agent lancé par l'orchestrateur, avec son propre contexte. Hook : script exécuté par Claude Code avant chaque appel d'outil. Séparation complète : toutes les valeurs d'un groupe sont inférieures à toutes celles de l'autre.
